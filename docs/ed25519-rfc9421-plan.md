# Ed25519 + RFC 9421 dual-stack plan (not implemented)

Status: Draft · Release gate: Birchtree is not production-ready until this
plan is implemented and its interop exit test passes.

This document is a plan only. It implements nothing. The tree today is
RSA-only: no Ed25519 key is generated, published, or verified anywhere,
and no RFC 9421 `Signature-Input`/`Signature` path exists. An RFC
9421-shaped request is refused (401), never accepted and never crashes,
pinned by `rfc9421_shaped_request_is_refused_without_state_change` in
`tests/phase6_federation.rs`. That test must keep passing until this plan
lands; the landing commit must replace the refusal with the inbound policy
below and record the red-to-green run.

## 1. Goals

- Add Ed25519 + RFC 9421 as the default outbound path where the peer
  supports it, with legacy RSA retained only as an explicit compatibility
  path for RSA-only peers.
- Never silently downgrade: a failed Ed25519 sign for an RFC 9421 peer
  fails the delivery; it never falls back to RSA for that peer.
- Keep inbound compatible during migration: verify RFC 9421 and legacy
  RSA; unsigned stays refused (401, no state change).
- Prove interop against a live Mastodon 4.7 lab run, not by unit fixtures
  alone.

Non-goals: Ed25519-only outbound, RSA key rotation, proxy/streaming work
(see Workstream D), and any change to the AWS-LC RSA provider
(`vendor/activitypub_federation/src/rsa_provider.rs`).

## 2. Key generation and publication

- Generate one Ed25519 key per local actor alongside the existing 2048-bit
  RSA key. No key rotation: the RSA `keyId` stays byte-identical and
  already-published RSA public keys keep verifying.
- Reuse the `src/activitypub/key_generation.rs` single-flight pattern:
  per-account gate, generation on a blocking thread, atomic store insert
  decides the winner and discards losing generated keys.
- Store the Ed25519 private key sealed like other actor secrets (see Work
  package 1.3); never log key material. Persist the public key with the
  actor record.
- Publish the Ed25519 public key in the actor document next to the RSA
  `publicKey`, without changing the RSA `keyId` value. Use a distinct key
  fragment for the new key (for example `#ed25519-key`) so existing
  verifiers that resolve the RSA fragment are unaffected. Document the
  exact JSON shape against the Mastodon 4.7.3 serializer before coding.
- Acceptance: fresh actors publish both keys; restarted nodes load both;
  old RSA-only documents still verify; private material is never logged.

## 3. Per-peer capability detection

- Detect RFC 9421 support explicitly per peer; never assume it from one
  successful delivery. Candidate signals (confirm against Mastodon 4.7.3
  and Misskey/Sharkey targets before coding): the peer actor document
  advertises an Ed25519-compatible key, or a cached peer record marks RFC
  9421 acceptance after a verified inbound RFC 9421 request.
- Cache the decision per host/peer with a bounded, expiring entry; a
  missing entry means RSA-only. Capability downgrade (RFC 9421 to RSA-only)
  must be an explicit, logged operator or protocol event, never an
  automatic fallback inside the send path.
- Acceptance: an RSA-only peer is never sent RFC 9421; a dual-stack peer is
  never sent legacy Cavage for new deliveries; stale capability entries
  expire rather than pinning a peer forever.

## 4. Outbound policy (no silent downgrade)

- A peer marked RFC 9421-capable gets RFC 9421 signatures only
  (`Signature-Input` / `Signature` with an `rsa-v1_5-sha256` or Ed25519
  signature as negotiated; Mastodon 4.7 uses `rsa-v1_5-sha256` for RSA
  compatibility). A failed Ed25519/RFC 9421 sign fails that delivery and
  reports a sanitized error; the send path must not retry the same
  delivery as legacy RSA.
- Outbound to RSA-only peers keeps `sign_legacy_rsa_sha256` under the
  compatibility exception in `docs/birchtree-rsa-prod.md`.
- Covered components, date-and-covered-content headers, digest algorithm,
  and key-id selection must match what Mastodon 4.7 expects; confirm field
  by field against a live 4.7 capture before locking the signer.
- Acceptance: forced Ed25519-sign failure for an RFC 9421 peer yields a
  failed delivery and no legacy-signed bytes on the wire (assert in a
  network-capture or test-double harness); RSA-only peers still receive
  legacy `rsa-sha256`.

## 5. Inbound verification

- Verify RFC 9421 (`Signature-Input`, `Signature`, covered content,
  `Content-Digest`, key resolution to the claimed peer key, clock-skew
  bounds, replay/idempotency via the existing activity-seen path) and keep
  verifying legacy draft-Cavage RSA via `verify_legacy_rsa_sha256`.
- Unsigned requests stay refused (401, no state change), as today. A bad
  RFC 9421 signature is rejected the same way: 401 with no activity
  recorded, no follow created, and no fetch enqueued.
- Fetch the claimed signing key over the existing SSRF-safe federation
  network client with size, timeout, and redirect limits; never accept a
  key delivered inside the unsigned request body as authoritative.
- Acceptance: one Mastodon 4.7-shaped RFC 9421 request accepted, one legacy
  draft-cavage request accepted, one bad signature rejected with no state
  change.

## 6. Interop exit test (release gate)

All three must pass on the release build, proven by a live 4.7 lab run
plus committed regression tests:

1. One Mastodon 4.7-shaped RFC 9421 request accepted and applied.
2. One legacy draft-cavage request accepted and applied.
3. One bad-signature request rejected (401) with no state change
   (`activity_seen` false, no follow row, no queued fetch).

Until then, `rfc9421_shaped_request_is_refused_without_state_change`
remains the pin: RFC 9421-shaped requests are refused without state
change. The landing commit must show that test replaced or extended by
the accept/reject trio above, with the lab evidence linked from
`docs/logs/`.

## 7. Landing sequence

1. Key generation + publication + actor-document fixtures.
2. Inbound verification behind the same refusal default (still 401 until
   the trio in §6 passes).
3. Capability detection + outbound policy with the no-downgrade guard.
4. Live 4.7 interop run; flip the pin test; record evidence.
